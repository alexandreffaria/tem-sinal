# Audit, 2026-11-12

State of CellSignalMapper before it moves to the Geode-style flow (board of task
cards, one PR per card, second-session review). Read in full: every Kotlin file,
the manifest, Gradle files, Firestore rules, the CI workflow. 812 lines of Kotlin,
no real tests, last code change 2025-06-13.

Not verified on a device: there is no Android SDK on the dev machine, so nothing
here was built or run. Findings marked **(likely)** follow from the code and the
Android docs but need one run on a phone to confirm.

## What the app does today

1. `MainActivity` asks for location + phone state, signs in to Firebase
   anonymously, starts `LoggerService` when you press LOG.
2. `LoggerService` loops every 5 s: asks for one fresh GPS fix (5 s timeout),
   reads the latest dBm from a `TelephonyCallback`, finds the *registered* cell in
   `allCellInfo`, and appends a JSON line to `files/signal_log.json` **only if**
   the tower's MCC/MNC equals the SIM's, and the phone moved > 10 m or the dBm
   changed.
3. "Send my data" uploads the file as one Firestore batch to `signal_logs` and
   deletes the file.
4. Nothing reads the data back. There is no map. Firestore rules forbid reads.

## 1. Bugs that lose or corrupt data

| # | Finding | Where | Impact |
|---|---|---|---|
| B1 | `"%.5f".format(lat).toDouble()` uses the phone's locale. In pt-BR the decimal separator is a comma, so it produces `"-22,95123"` and `toDouble()` throws. The exception escapes the coroutine and **kills the app**. | `LoggerService.kt:134-135` | **(likely)** Every phone set to Portuguese crashes on the first good fix. That is most phones in Brazil. |

| B6 | The dBm comes only from `TelephonyCallback`, which exists from API 31. `minSdk` is 30, so Android 11 phones never get a signal value; every ping is BAD. | `LoggerService.kt:66`, `build.gradle.kts` | Android 11 users collect nothing. |
| B7 | No permission check before starting the service. `allCellInfo` throws `SecurityException` without fine location, uncaught: crash. On Android 13+ the notification permission is never asked for. | `MainActivity.kt:93`, `LoggerService.kt:157` | Crash if the user declined. |

| B9 | Point id is `UUID(carrier|lat|lon|dBm)`. Two people (or two days) with the same reading at the same spot overwrite each other. | `LoggerService.kt:187` | Crowdsourced counts collapse; timestamps are lost. |
| B10 | `cellSignalStrengths.firstOrNull()` is not necessarily the serving cell: on 5G NSA the first entry is often the LTE anchor, sometimes NR. The value isn't tied to the cell identity that gets logged. | `LoggerService.kt:42` | Mislabelled strengths. |

## 2. What it doesn't record (the emergency-planning gap)

The goal is "can I get help from this spot?". The app currently answers a
narrower question: "how strong was *my own carrier* where I *had* a signal?".

| # | Gap | Why it matters |
|---|---|---|
| D1 | **No-signal points are thrown away** (`dBm == -999` → BAD → not logged). | "No signal here" is the most valuable fact for planning. |
| D2 | **Emergency-only service isn't recorded.** When your carrier has no coverage the phone can still camp on another network and call 190/192/193/112. `ServiceState` says so (`EMERGENCY_ONLY` / `isEmergencyOnly`). | Tells a climber "you can call for help here even without your carrier." |
| D3 | Readings from another carrier's tower are dropped (`isSameCarrier`, `LoggerService.kt:180`). That also drops national roaming and RAN sharing, both common in rural Brazil. | Throws away coverage of exactly the kind we want. |
| D4 | Only one SIM is read. Dual-SIM phones (very common in Brazil) can report two carriers at once. | Free second carrier per sample. |
| D5 | No GPS accuracy, altitude, or fix time is stored. | On a wall, 50 m vertical is the difference between signal and none. A 60 m-accuracy point shouldn't paint a precise spot. |
| D6 | Firestore rules allow any signed-in client to write anything, any shape, any size, and to overwrite existing documents. No App Check. | Anyone can poison or bloat the map. |
| D7 | Only one generic `dbm` value. For LTE/NR, RSRP + RSRQ + SINR say much more about whether a call or SMS will get through. Network type (2G/3G/4G/5G) isn't stored either. | 2G at −105 dBm can be fine for SMS; LTE at −115 RSRP is borderline. |
| D8 | Carrier names come from a hardcoded MCC/MNC table that is incomplete and dated (Oi mobile was split among TIM/Vivo/Claro in 2022). | Store the raw PLMN and `operatorAlphaLong`; map to names on the server. |
| D9 | No schema version on entries. | Every change above breaks old rows silently. |

### Can we measure several carriers at once?

Partly. What works and what doesn't on a normal (non-system) Android app:

- **Neighbor cells: yes, from `getAllCellInfo()` / `requestCellInfoUpdate()`.**
  The modem reports the serving cell plus the neighbors it measures, with
  strength. The catch: neighbors are mostly *your* carrier's (the network tells
  the modem which frequencies to measure), and for non-registered cells MCC/MNC
  are usually missing; you get RAT, ARFCN, PCI and strength. The ARFCN can often
  be traced to a carrier, since ANATEL licenses frequency blocks per operator and
  region, but the mapping is approximate and belongs on the server.
- **Dual SIM: yes, reliably.** `TelephonyManager.createForSubscriptionId()` per
  active subscription gives a registered cell and strength for each SIM. A user
  with Vivo + TIM records both in every sample.
- **Emergency-only state: yes.** See D2. It doesn't say *which* network would
  carry the call, but it does say that one exists.
- **A full scan of every carrier: no.** `requestNetworkScan` needs
  `MODIFY_PHONE_STATE` or carrier privileges, which Play Store apps can't get
  (the manual network selection screen in Settings is a system app).
- **Crowdsourcing is the real multi-carrier answer.** Every user brings their
  own carrier(s). That only works once B9 and D3 are fixed, so readings add up
  instead of overwriting or being filtered out.

## 3. The missing half: the map

The companion repo `alexandreffaria/signal-heatmap` (**public**, last commit
2025-05-30) is the old viewer: a Go server on Cloud Run that loads the whole
`signal_logs` collection into memory at start, polls Firestore every 10 s, and
serves every raw point as JSON to a Leaflet page.

| # | Finding | Where |
|---|---|---|
| M1 | A public repo commits `data.json`: 241 raw points with exact coordinates, millisecond timestamps and cell IDs, from one ~14-hour session inside an area under 1 km across. A cluster like that is close to a home address, and it stays in git history. | `signal-heatmap/data.json` |
| M2 | `/data` publishes every raw sample. Anyone can rebuild contributors' movements. | `main.go` |
| M3 | Full collection load on every start + all points in one response: cost and memory grow with the data, without limit. | `main.go` `loadAll` |
| M4 | Leaflet loaded from unpkg with no version pinned. | `static/index.html` |
| M5 | No keys were ever committed to its history (checked). | |

That's all the data there is, so nothing has to be migrated and the
architecture is open. Proposed shape, whichever backend is chosen:

```
phone (offline queue) ──► ingest (validated) ──► raw samples (private)
                                                     │ scheduled job
                                                     ▼
                         public link ◄── static hex files on a CDN (H3, per-carrier stats)
                         (MapLibre page)
```

Raw samples never leave the private side, and the public side is static (no
cost at rest, no server to keep up for viewers, cacheable offline later).
Where ingest lives and what the hexes show are owner decisions (president
cards 20261113p3kn and 20261113a7do).

## 4. Tests and checks

No unit tests beyond the template. The logic worth testing (dedupe/move
detection, PLMN parsing, entry serialization, upload chunking) is tangled into
`LoggerService`'s loop. Extract it into plain functions as the bug fixes touch
it, with a JVM test per fix. CI should run `./gradlew lintDebug testDebugUnitTest
assembleDebug` on every PR.
